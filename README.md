**An attempt at a fully open-source, multi-chain hardware wallet that anyone can assemble from commodity parts — no soldering.**

- **Initial scope**: Bitcoin + EVM (Ethereum / ERC-20 / major L2s)
- **Hardware**: SeedSigner-compatible commodity parts, assembled without soldering
- **Target cost**: roughly ¥8,000–13,000 (USD 55–90) per unit
- **Status**: the software stack (signing, transport, UI, SD-card exchange) is implemented and tested; the firmware has **not yet run on the target hardware**

---

## The problem this project addresses

Existing open-source hardware wallets fall into three groups.

| Category | Examples | Problem |
|---|---|---|
| Fully open, but Bitcoin-only | SeedSigner, Krux, Specter DIY | Cannot be used multi-chain |
| Multi-chain, but hardware/firmware closed | Ledger and others | Not "fully open source" |
| Multi-chain with open firmware | Trezor, BitBox02, Keystone | Hardware design closed, or not self-buildable |

This project aims at the intersection: **buildable by anyone from commodity parts** × **multi-chain** × **fully open source**. The hardware reuses the proven SeedSigner parts list; the software is written from scratch to support BTC + EVM.

---

## Three design principles

1. **Keys know nothing about chains** — key management, randomness and signing primitives live in `core`; chain-specific logic lives in `apps`. Adding a chain means adding an app, and does not require re-auditing the core.
2. **Sign only what is displayed (clear signing)** — per-chain transaction parsing and human-readable display are mandatory; blind signing is not allowed. BTC uses PSBT, EVM uses [ERC-7730](https://eips.ethereum.org/EIPS/eip-7730) descriptors.
3. **Secrets die with the power (stateless)** — the seed exists only in RAM and is never written to flash. Power off, and it is gone. The SD card is removed after boot.

---

## Why there is no secure element (SE)

"Fully open source" and "chain signing inside an SE" are not simultaneously achievable with today's parts.

| SE | Curves | Conclusion |
|---|---|---|
| ATECC608A/B | NIST P-256 only | **Cannot sign secp256k1** (used for key storage/attestation in BTC/ETH designs) |
| OPTIGA Trust M V3 | NIST/Brainpool | [Used by Trezor Safe 3/5, but the seed does not live in the SE; signing happens on the MCU](https://trezor.io/learn/security-privacy/how-trezor-keeps-you-safe/secure-elements-in-trezor-safe-devices) |
| Java Card based | Some support secp256k1 | Leads to a design without a display, badly degrading UX |
| TROPIC01 | Auditable SE | [Used by Trezor Safe 7](https://trezor.io/learn/security-privacy/how-trezor-keeps-you-safe/secure-elements-in-trezor-safe-devices); currently almost impossible to buy as an individual |

This project therefore chooses **no SE and a stateless design**, and documents the residual risk of physical attacks in [docs/05-threat-model.md](docs/05-threat-model.md). Physical-attack resistance is compensated by multisig, passphrases, keeping balances small, and powering the device off after use.

### Try it on your PC (no hardware required)

The development CLI can sign real PSBTs, preview the device screens, and simulate the
microSD exchange against a FAT32 image file:

```bash
cd firmware && zig build
./zig-out/bin/zhww help
# sign a PSBT from stdin, show what would be signed, render device screens,
# exchange PSBTs over a FAT32 image (as the microSD would), and more
```

## Language policy

**Everything in this project is written in English** — user-facing text, documentation, code
comments, test descriptions, commit messages and issue replies — so that anyone in the world can
use it, review it and contribute to it.

The device UI is English only (the 240×240 screen shows plain ASCII), and the firmware has no
Japanese font embedded. Translations of the documentation into other languages are welcome as
additional files (for example `README.ja.md`), but English stays the source of truth.

## Development process and LLM usage

**This project is developed with heavy LLM assistance.**

| Role | Owner |
|---|---|
| Design decisions, requirements, acceptance | Human |
| Design documents, code, tests, documentation | LLM (coding agents) |
| Verification (running tests, cross-checking against official vectors) | Automated tests + human review |

Most of the Zig implementation (`firmware/src/`), the test suites (`firmware/tests/`) and the
design documents in `docs/` were generated by LLMs. A human reviews them, but **generated code
can contain mistakes**. So far, testing has found **11 bugs in LLM-generated code**, including
three memory-safety issues (a dangling slice into a by-value struct, a dangling pointer into a
loop-local, and a self-referential RNG pointer returned by value) and one case where the
*reference implementation used as an oracle* was wrong, not this code.

Because of this, passing tests is **not** treated as proof of safety here. Unverified areas are
stated as unverified. Pull requests, corrections and reviews are very welcome.
